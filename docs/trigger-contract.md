# 当前触发入口与阶段边界

记录日期：2026-09-19。用途：澄清现有实现，并记录后续完整流程必须考虑的权限约束；本记录不表示阶段工作流已实现。

## 已实现的触发条件

| 事件 | 执行条件 | 进入位置 |
|---|---|---|
| 新建 Issue | 创建时已经带 harness 标签；操作者与重跑操作者均为仓库所有者 | work → loop.py |
| 新增 Issue/PR 对话评论 | 评论从 /harness 开始，且通过完整命令解析；操作者与重跑操作者均为仓库所有者 | work → loop.py |
| 手动 Run workflow | 仓库所有者选择允许的分支，填写任务号和 instruction | work → loop.py |

只监听 issues.opened 和 issue_comment.created。给已有 Issue 补标签、编辑 Issue、编辑已有评论、普通 push 均不是本工作流的执行入口。评论触发无需 Issue 带 harness 标签。普通评论或未授权操作者可能产生事件对应的 skipped 运行记录，但不会执行开发 Job。

Issue/评论入口使用主线流程；测试分支只支持手动 dispatch。新建带标签的 Issue 默认只读澄清；正文模板选择直接实施可跳过默认澄清。/harness clarify 或 /harness 澄清强制澄清；publish/发布走已有结果发布；stop/停止记录停止。其他指令交给 Agent，不能视为正式阶段批准协议。

## 触发不是阶段切换

所有入口进入同一个调度脚本，没有分别触发 PRD、设计、开发、验证的机制。普通执行读取任务历史与工作区，由 Agent 决定提问或实现；实现后运行浏览器检查。生成可发布结果才执行 publish，随后 record 保存结果。暂停等待输入时当前 Job 结束，不会同时启动全部后续阶段。

现有 waiting_input/running/waiting_review 等是执行状态，不是 PRD/设计/开发阶段。完整阶段状态、阶段产物审查与批准绑定版本尚未实现。

## 后续完整流程的权限约束

用户提出：公开 Issue 中任意评论者不能启动执行。当前 owner-only 只适合个人实验；组织成员账号不等于组织名，不能直接用于团队。

团队授权方案尚待确定：需要区分谁能启动、回答澄清、批准产物；审批必须关联明确的产物版本。不能把任意自然语言回复或 Agent 对批准的猜测当成人工授权。Agent 可提出需要澄清/审查的判断，但不能替代人的批准。

拟定原则：入口事件只负责唤醒任务；进入哪个阶段应由持久化任务状态和已有材料决定。此原则尚未落地，不应写成现有能力。
