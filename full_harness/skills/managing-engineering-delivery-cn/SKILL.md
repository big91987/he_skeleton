# 研发交付管理

## 使命与阶段

把已确认的需求和架构转化为仓库原生、工具无关、可以持续接力的公共交付事实。

本 Skill 从“具备研发准备条件”开始，覆盖：

```text
G2 研发准备
→ 里程碑规划
→ 任务拆解与分发
→ 切片实现与持续集成
→ 里程碑验证
→ G4 版本交付
```

需求定义 Skill 决定做什么，架构 Skill 决定系统如何组织，本 Skill 决定如何拆、按什么顺序做、由谁做、如何验证和交接。具体任务再路由给适合的 SDD、TDD、LOOP、研究、评审或人工流程。

## 核心原则

### 维护公共事实，不维护个人过程

公共仓库必须让没有参与历史对话、没有安装相同 Skill 的人或 Agent 接手工作。提交到公共区的内容包括：

- 阶段目标、里程碑和验收门槛；
- 任务包、依赖、负责人和公共状态；
- 对 PRD、AC、原型、HLD、LLD 和契约的追踪；
- 代码、测试、共享验证入口、验证证据和交接结果。

个人 Prompt、会话、思考过程、缓存、checkpoint、工具内部状态和临时计划默认留在本地并由 `.gitignore` 排除。

### 只增加必要结构

只使用四类公共交付事实：

1. **阶段交付计划**：说明整体目标、里程碑、依赖、关键路径和当前状态；
2. **里程碑**：表达一个可集成、可演示或可验收的阶段结果；
3. **任务包**：表达一个可独立领取、实现、验证和交接的工作单元；
4. **验证记录**：表达里程碑或版本是否达到退出条件及其证据。

模块、执行工具、人员和 Agent 是任务属性，不为它们另建无独立生命周期的管理对象。不要为了显得完整而创建全局 HANDOFF、DECISIONS、DEMO、RISKS 等重复文档；只有项目已有独立责任和维护需要时才复用或新增。

### 以结果和证据报告进度

使用任务状态、里程碑门槛、关键路径和阻塞说明进度。不要让人员主观填写无法验证的百分比。需要汇总比例时，从已完成任务或已接受里程碑计算，并明确计算口径。

## 首次进入与断点续传

开始前按以下顺序读取：

1. 项目指令和公共研发规则；
2. 当前阶段目标、PRD、AC 和原型；
3. HLD、相关 LLD、ADR、接口契约和技术验证结论；
4. 现有 `docs/delivery/` 或项目指定的公共交付目录；
5. 代码、测试、CI 和共享验证命令的实际状态。

如果公共交付目录已经存在，先恢复当前状态再继续：

- 读取总览、所有非终态任务和当前里程碑；
- 检查任务引用的权威文档是否变化；
- 检查状态、提交、验证证据和代码实际情况是否一致；
- 从最后一个未通过门槛或未完成任务继续；
- 不重新编号、不重复创建已经回答或完成的任务。

聊天记录不能成为恢复工作的必要输入。

## 工作流

### 1. 执行研发准备检查

判断当前阶段是否具备可执行基线：

- 阶段目标和非目标已经明确；
- P0 行为拥有可观察的 AC；
- 原型或外部交互契约足以约束实现；
- 当前任务需要的架构边界和接口契约已经明确；
- 技术未知项已经解决，或被拆成有明确结果的验证任务；
- 仓库有可用的开发、测试和集成入口，或已安排 Harness 建设任务。

不要要求所有 LLD 一次完成。某个切片需要的产品和技术契约清楚，该切片即可进入 `Ready`。

发现缺口时按责任返回：

| 缺口 | 返回位置 |
|---|---|
| 目标、范围、业务规则或 AC 不清 | 需求定义 |
| 模块责任、接口、状态或质量策略不清 | 架构设计 |
| 组件能力、版本行为或性能未知 | 技术验证任务 |
| 测试、环境、Fixture、诊断入口缺失 | Harness 建设任务 |

只有会导致任务无法正确实施或验收的缺口才阻塞。低风险细节写入任务假设，不逐项打断用户。

### 2. 建立阶段交付计划

从阶段目标派生 3～7 个以结果命名的里程碑。数量只是默认范围，按实际复杂度调整。

每个里程碑必须说明：

- 可观察的阶段结果；
- 进入条件和退出条件；
- 依赖的里程碑；
- 覆盖的需求、模块和主要风险；
- 集成、演示或验收证据。

优先采用端到端薄切片。不要默认按前端、后端、数据库、测试横向切成互相等待的里程碑。不要在没有用户期限时编造 D1～D10 或日期计划。

### 3. 拆分可独立领取的任务包

把里程碑拆成能够独立分配、合并、验证和交接的任务包。任务粒度以独立责任和可验证结果为准，不以固定小时数为准。

合格任务必须：

- 在不读取历史聊天的情况下可以理解；
- 对应一个明确结果和一组可观察 AC；
- 标明权威输入和交付物；
- 标明依赖、影响范围和接口边界；
- 拥有可执行或可复现的验证方式；
- 完成后能被下一任务或里程碑直接消费；
- 尽量形成纵向切片，减少多人同时修改同一热点文件。

任务内部的逐步编码计划属于执行工具。不要把任务包继续拆成两分钟级实现步骤，也不要把 OpenSpec、Trellis 或 Superpowers 的私有工作目录复制到公共区。

### 4. 建立依赖、优先级和并行计划

区分：

- **硬依赖**：前置结果未完成时，后续任务无法正确实施或验证；
- **软依赖**：可以使用 Mock、契约或临时实现并行推进；
- **冲突范围**：两个任务会修改同一接口、迁移或热点模块；
- **关键路径**：决定当前里程碑最早完成时间的任务链。

根据依赖和交付风险确定优先级，不按提出顺序排序。只有任务状态为 `Ready` 且硬依赖满足后，才可正式领取。

不要默认规定分支策略、每日合并次数、单人 WIP、会议节奏或功能冻结。用户给出的期限可以用于提出排期建议，但不能自动推导“某日以后只修缺陷”等流程政策。项目已有规则时遵循；确有并行冲突或交付风险时，把新规则标为待确认提案并说明理由。

### 5. 为任务选择执行方式

为每个任务标注推荐的执行类型，但不把团队绑定到特定工具：

| 任务特征 | 推荐执行类型 |
|---|---|
| 行为或跨模块契约仍需展开 | SDD / OpenSpec 类流程 |
| 行为明确且可自动测试 | TDD / Superpowers 类流程 |
| 有量化目标，需要反复实验 | LOOP / 优化循环 |
| 外部组件事实不确定 | Research / Validation |
| 只检查规范、实现或安全性 | Review |
| 权限、环境或业务批准 | Human Action |

执行者可以换用任何兼容工具。公共任务的目标、AC、接口和证据要求保持不变。

### 6. 建立 Harness 验证闭环

对每个任务定义最小验证契约：

- 准备环境的方法；
- 最小验证命令或人工步骤；
- 成功和失败的可观察结果；
- 必须保留的测试、日志、报告或截图；
- 下一个人如何复现。

检查仓库是否有稳定的共享入口，例如 setup、unit test、integration test、lint、build、migration、seed、smoke、end-to-end 和诊断日志。只要求当前阶段实际需要的入口。

缺失的 Harness 能力要形成独立任务包，并与使用它的功能任务建立依赖。Harness 的实现交给具体编码流程，本 Skill 只定义需要的反馈环、验收条件和公共入口。

### 7. 写入公共交付区

默认使用：

```text
docs/delivery/
├── README.md
├── milestones/
├── tasks/
└── verification/
```

项目已有等价结构时沿用，不并行创建第二套事实源。完整字段和模板见 `references/public-delivery-contract.md`。

任务文件是任务状态事实源；`README.md` 是全局进度投影。多人并行时主要更新自己负责的任务文件，由交付负责人或本 Skill 汇总总览，避免所有人频繁修改一张大表。

需要 Excel、看板或 Issue Tracker 视图时，指定一个可写事实源。默认由任务文件生成或同步出其他视图；不得让多个载体都被人工独立维护。

### 8. 分发、跟踪和处理变化

领取任务时记录负责人或执行 Agent、开始时间和当前基线。执行期间只维护公共事实：

- 状态和阻塞；
- 已形成的代码、契约和验证证据；
- 会影响其他任务的接口变化；
- 与原计划的实际偏差；
- 下一位接手者需要的上下文。

需求范围改变时，先判断影响层级：

- 只影响任务实现：更新任务并记录变化；
- 影响多个任务或里程碑：更新交付计划和依赖；
- 改变产品承诺或 AC：返回需求定义；
- 改变模块责任或公共契约：返回架构设计并记录 ADR。

不要在任务文件中重新发明 PRD 或架构决策。

### 9. 完成任务和交接

任务进入 `Done` 前必须具备：

- 交付物已经存在并可定位；
- AC 已逐条验证；
- 共享验证入口通过，或明确记录不能自动化的证据；
- 相关接口、迁移、配置和文档同步；
- 设计偏差已经回写到正确的上游文档；
- 实施结果、已知限制和下一步已经写入任务文件；
- 指定评审完成。

提交数量、代码生成数量或 Agent 声称完成都不能单独作为完成证据。

### 10. 执行里程碑和版本门禁

里程碑只有在退出条件逐项满足、任务完成且集成证据成立后才能标记为 `Accepted`。版本交付至少检查：

- 当前范围的 PRD/AC 追踪闭环；
- 关键用户旅程或系统链路通过；
- 环境能够按公共说明复现；
- 故障、回滚、数据迁移和运营准备达到本阶段承诺；
- 未完成项、已知风险和后续范围已明确；
- Release 或等价交付物可定位。

只报告证据支持的状态。验证未完成时，写 `Ready for Review` 或 `Blocked`，不得写成已交付。

## 状态模型

任务使用：

```text
Draft → Ready → In Progress → In Review → Done
                    ↘ Blocked ↗
```

范围取消的任务保留文件并标记 `Dropped`，说明原因和替代任务，避免后续 Agent 重复创建。

里程碑使用：

```text
Planned → Active → Ready for Review → Accepted
              ↘ Blocked ↗
```

## 交付审查

生成或更新计划后，使用 `references/delivery-review-checklist.md` 做一次审查。重点检查：

- 是否遗漏 PRD、AC、原型或架构能力；
- 是否存在重复任务或同一事实的多个维护位置；
- 是否把架构决策偷偷交给编码 Agent；
- 是否把任务拆成技术层而没有可验证结果；
- 是否有无法复现、无法验证或依赖聊天记录的任务；
- 是否存在无必要的文档、状态、ID、流程和工具绑定；
- 是否明确关键路径、阻塞和下一批可领取任务。

用户要求压力审查时，可配合 Batch Grill；把每轮确认立即写回公共任务和计划，下一轮从现有文件继续，不重复询问已确认事项。

## 标准输出

每次交付管理工作结束时，直接报告：

1. 当前阶段和当前里程碑；
2. 已完成、进行中、阻塞和下一批 Ready 任务；
3. 关键路径与主要风险；
4. 本轮更新的公共文件；
5. 需要用户决定的事项；
6. 是否具备继续分发、里程碑评审或版本交付的条件。

输出产品和工程事实，不写 Agent 的内心独白、长篇推理过程或工具内部状态。

## 公共交接验收标准

任意新成员或新 Agent 只读取以下内容，就应能够接手一个任务：

```text
公共交付总览
→ 自己领取的任务包
→ 任务引用的权威需求和架构文档
→ 仓库共享开发与验证入口
```

如果仍必须阅读历史聊天、个人笔记或特定工具的隐藏目录，先补齐公共任务包，再继续分发。
