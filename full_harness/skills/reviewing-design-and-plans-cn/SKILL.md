# 设计与计划评审

## 核心原则

一次只评一个阶段 Gate。先冻结本轮目标和文档集合，再依据当前文件审查；默认只读，不替 Owner 决策，不把后续阶段尚未完成的工作误判为当前阶段缺陷。

公共仓库中的产品、架构、交付和验收文档是团队事实源。Trellis、OpenSpec、Superpowers 或其他个人工具产物可以被评审，但不能静默改写公共基线。

## 选择 Gate

| Gate | 主评审对象 | 通过后进入 |
|---|---|---|
| `G1 产品基线` | 广义 PRD、User Story、AC、原型和产品决策 | HLD |
| `G2 HLD READY` | HLD、领域责任、关键链路、架构决策、质量与恢复原则 | LLD |
| `G2 LLD READY` | LLD、术语、状态机、数据/API 契约、模块接口和失败处理 | 研发计划 |
| `G3 PLAN READY` | 里程碑、任务包、依赖、Owner、验收方法和交接条件 | 编码实施 |

用户显式指定 Gate 时服从用户。未指定时按主文档判断；判断会改变评审范围时，先用一句话说明采用的 Gate。

不要自动跨 Gate：

- PRD 通过不代表 HLD 已完成。
- HLD 通过不要求 LLD 已写完。
- 计划通过不代表代码或环境已验证。
- 实现验收和 Release Ready 转交代码审查、浏览器验收与目标环境验证流程。

需要各类工具产物映射或公共/本地边界时，读取 [references/workflow-mapping.md](references/workflow-mapping.md)。

## 冻结评审边界

评审开始时记录：

```text
Gate 与评审模式：初审 / 复审 / 整改闭环
本轮目标和可观察结果
主评审文档
只读上游基线
必要的代码、配置、测试或环境事实
明确非目标和不得改变的已接受决定
当前 Git commit、分支或文件快照
本轮可修改路径：默认无
```

“完整评审”指覆盖本轮目标相关的完整决策链，不是扫描整个仓库。只加载会证明或推翻当前 Gate 的文档和事实。

## 建立文档责任

先确定每种事实由谁拥有：

| 事实 | 权威产物 |
|---|---|
| 产品目标、范围、非目标、角色、业务规则 | PRD / 产品决策 |
| 可观察行为和验收边界 | User Story / AC / 原型交互规范 |
| 模块责任、架构流、取舍、兼容和恢复原则 | HLD / ADR / 决策台账 |
| 字段、状态、接口、数据和错误契约 | LLD / 契约文档 |
| 实施顺序、任务 Owner、验证责任 | 公共交付计划 |
| 运行结果和验收证据 | 验证报告 / 测试与环境证据 |

一个文档可以承担多种责任，但同一事实只能有一个最终权威来源。下游只能承接或引用上游决定，不能换一种说法悄悄改掉。

## 执行评审

### 跨 Gate 前置对象追踪

在当前 Gate 范围内，对每条关键旅程的第一个前置条件向前追溯一步。若旅程依赖一个已经存在的持久对象，记录：对象来源、创建或接入责任人、受支持操作方式、可用性核验与交接、后续变更与退出、失败恢复及验收证据。

`预配置`、`预置`、`已存在`、`外部提供`、`运维初始化` 是需要追踪的信号，不是闭环证据。事实源只说明“状态以谁为准”，不能替代“谁能通过什么权威命令路径改变状态”。数据库直改或一次性 migration 默认只算实现机制；只有上游明确接受该运营模式，并具备规程、权限、校验、恢复、审计和持续变更路径时，才可作为受支持入口。

发现来源缺口时只判当前 Gate：G1 要求运营责任和首次可用旅程；HLD 要求责任域、事实源、命令与调和流；LLD 要求可实现的接口、状态、错误、幂等和权限契约；G3 要求任务、依赖、回滚和验证责任。不要用后续 Gate 的细节要求越级否决前一 Gate。

### G1 产品基线

检查：

1. 目标用户、业务价值和可观察结果是否明确。
2. 范围、非目标、阶段边界和基本业务规则是否清楚。
3. 关键用户旅程是否有 User Story、AC 和必要原型承接。
4. 角色、权限、资源生命周期和异常路径是否闭合。
5. 每个关键旅程依赖的持久前置对象是否有来源、首次可用、核验、变更和退出路径；托管或外部提供时是否有明确运营与验收边界。
6. 是否过早绑定组件、Kubernetes 对象或未经确认的实现机制。

需求发现和产品定义仍由 `defining-platform-products-cn` 负责；本 Skill 负责形成后的独立兜底审查。

### G2 HLD READY

检查：

1. 每项关键产品能力是否有明确责任域和事实源。
2. 数据流、控制流、调用流、计量流是否区分且能闭环。
3. 模块边界、依赖方向和外部系统接缝是否清楚。
4. 关键取舍、兼容、故障、恢复和演进边界是否足以指导 LLD。
5. 被下游稳定引用的控制面对象是否同时具有权威事实源、唯一写入责任、创建或接入命令路径以及调和边界。
6. 是否遗漏 PRD 能力，或为了未来引入没有当前责任的对象、ID、层和机制。

### G2 LLD READY

检查：

1. HLD 的每项责任和决策是否有 LLD 承接。
2. 关键术语、主键/外键、字段、状态机、接口、错误和幂等语义是否明确。
3. 同步/异步边界、执行记录、失败恢复和可观测责任是否可实现。
4. 模块间 DTO、数据库记录、供应商对象和产品对象是否避免混用。
5. 前置对象的创建或接入、校验生效、变更退出是否有接口、权限、错误、幂等和恢复契约。
6. 是否达到编码 Agent 可以实现且不会自行补产品或架构决定的程度。

### G3 PLAN READY

检查：

1. 每项批准的需求和设计是否映射到任务与验证责任。
2. 每个任务是否有一个主要行为结果、明确 Owner、依赖和验收方法。
3. 输出是否先于使用，迁移、兼容、回滚和高风险步骤顺序是否正确。
4. 路径、接口、命令、环境和权限是否真实可行。
5. 首次部署之外，持续运营所需的对象接入、变更、恢复和验收任务是否承接上游契约。
6. 每个任务是否能独立领取和交接；没有独立结果的碎片应合并，可独立回退的行为应拆分。

## 控制评审深度

默认使用 `AUTO`：主流程做完整检查，只对以下高风险部分加深：

- 权限和信任边界；
- 配额、计量、费用；
- 删除和不可逆数据变化；
- 并发、幂等、状态机；
- 对外协议兼容；
- 生产启停、回滚和恢复。

不要为了一次低风险审查新增脚本、状态库或复杂台账。未来测试结果在设计和计划阶段标记为“后续验证”，只要求现在能说清验证责任、环境和通过标准。

## 分类结论

| 类型 | 含义 |
|---|---|
| `BLOCKER` | 主链无法成立、权威文档冲突，或存在可达的严重安全/数据风险 |
| `REQUIRED` | 当前 Gate 通过前必须补齐 |
| `CONCERN` | 不阻断，但需要 Owner 接受的现实风险 |
| `NEXT STAGE` | 属于编码、集成、验证或发布阶段 |
| `OUT OF SCOPE` | 真实问题，但不属于本轮范围 |
| `DECISION REQUIRED` | 必须由 Owner 决定产品、范围、架构取舍或风险接受 |

所有 `BLOCKER` 和 `REQUIRED` 必须给出：违反的当前 Gate 条件、当前证据、影响链和最小修正目标。不要只给建议性措辞。

## Owner 决策与整改

默认只读。发现以下情况立即停在 `DECISION REQUIRED`：

- 改变产品范围、非目标、角色权限或用户体验；
- 改变架构方向、模块主责、公共契约或风险承担；
- 新增可独立交付的机制、状态、服务或数据事实；
- 缺少修改权或存在多个同样合理的方案。

用业务语言说明“现在是什么、改动后是什么、为什么需要决定、推荐什么”。多个相关问题使用项目约定的 Batch Grill 集中确认，避免逐个打断 Owner。

Owner 授权后才能整改：

1. 重新确认问题仍存在。
2. 先修改拥有该事实的权威文档。
3. 只同步受影响的下游引用、任务和验收条目。
4. 检查精确 diff 和完整影响链。
5. 对修复后的快照进行复审；修改者不能仅凭“已修改”宣布通过。

## 简化检查

出结论前删除不必要的复杂度：

- 没有独立状态、规则、生命周期或权限的对象；
- 已有业务键可以表达却新增的 ID；
- 只为假想未来建立的层、适配器或配置；
- 同一事实的第二份权威来源；
- 为解释含糊名称而增加的大段说明。

可信演进点保留窄接口或明确引用即可，不提前实现未来机制。

## 输出格式

先给一句明确判定，再按以下顺序输出：

```text
Gate 与结论
主评审文档和快照
BLOCKER / REQUIRED
需要 Owner 决策的事项
非阻断风险与后续阶段事项
已确认闭环
下一步和允许修改的路径
```

可用结论：

- `G1 READY / NOT READY`
- `G2 HLD READY / NOT READY`
- `G2 LLD READY / NOT READY`
- `G3 PLAN READY / NOT READY`
- `DECISION REQUIRED`
- `AUDIT INCOMPLETE — RESUME REQUIRED`

不要在最终报告重放全部思考过程。报告当前事实、影响和下一步。

## 示例

任务：评审 Trellis 为“模型删除”生成的 `prd.md`、`design.md` 和 `implement.md`。

正确做法：以公共 PRD 和已接受生命周期决策为上游基线；先评 `design.md` 是否完整表达先停后删、依赖守卫、异步清理和审计，再评 `implement.md` 是否覆盖 API、状态、Worker、页面和验收矩阵。Trellis 文件与公共基线冲突时标记问题，不自动修改公共 PRD；需要改变删除语义时返回 `DECISION REQUIRED`。

## 常见错误

- 一次把 PRD、HLD、LLD、代码和发布全部判为同一个 Gate。
- 因后续测试尚未运行而否决 HLD 或计划。
- 把工具本地文件当成团队唯一事实源。
- 依据旧评审报告判断当前文件，而不读取当前快照。
- 为消除所有可能问题无限加深评审。
- 未经 Owner 确认就替换产品或架构决定。
- 把“预配置”“已存在”或 migration 当成前置对象来源已经闭环的证据。
