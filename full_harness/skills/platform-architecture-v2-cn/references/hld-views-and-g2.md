# HLD 标准视图与 G2

## 最小视图集

HLD 应按问题需要组合视图，不要求每个视图单独成文，但不得遗漏会改变实现方向的责任或约束。

| 视图 | 必须回答 |
|---|---|
| 目标与范围 | 建设结果、运营模式、成功标准、非目标和阶段边界是什么？ |
| 系统上下文 | 用户、运营者、外部系统、共享能力和信任边界是谁？ |
| 能力与领域 | 平台拥有哪些能力，领域责任、事实源和生命周期属于谁？ |
| 逻辑模块 | 模块承担什么结果、明确不负责什么、通过什么契约协作？ |
| 关键流程 | 调用、控制、计量、观测、身份和审计如何流动与失败？ |
| 信息与状态 | 核心对象、身份、状态机、策略、事件和一致性如何定义？ |
| 部署与故障 | 部署单元、网络、存储、故障域、扩展和恢复边界是什么？ |
| 质量属性 | 性能、容量、可用性、安全、运营、成本和迁移如何验证？ |
| 技术策略 | 候选实现覆盖什么、缺什么、如何验证、替换和退出？ |
| 演进与风险 | 可信变化、稳定契约、迁移路线、证据缺口和开放问题是什么？ |

视图只表达必要关系。简单系统可以合并视图，复杂系统按领域拆分；图形必须与文字契约一致。

## G2 进入 LLD 检查

满足以下条件才能声明 HLD 基线可进入 LLD：

- 需求基线已批准，范围变化已经显式处理；
- 目标、运营模式、领域责任和外部边界获得确认；
- 关键业务承诺都有 HLD 能力、流程、契约或质量属性承接；
- 主数据、运行事实、策略和计量事实的所有者明确；
- 同步关键路径、异步任务、幂等、失败、降级和恢复责任可解释；
- 部署单元、调用数据面、管理控制面、信任边界和主要故障域明确；
- 会改变整体方向的质量属性已经量化或具有验证计划；
- 技术选择映射到已确认责任，组件内部对象没有变成无意的公开契约；
- 高影响且难以逆转的选择具有决策记录、验证和退出路径；
- 所有未决项被分类为 LLD 输入、技术验证、阶段外风险或阻断项；
- 台账与 HLD 没有未解释冲突，用户或授权决策人确认共同理解。

## G2 结果

- `Pass`：可以进入 LLD；剩余事项不改变 HLD 方向。
- `Conditional Pass`：可以并行开始不受影响的 LLD，但列明阻断范围和验证期限。
- `Fail`：仍存在会改变领域、流程、部署、公开契约或关键质量属性的未知项。

G2 不是文档篇幅检查。图多、组件多或内容细不代表架构已经闭合。
