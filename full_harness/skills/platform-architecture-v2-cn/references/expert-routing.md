# 专家路由与协作契约

总体架构师先确定问题边界，再加载对应专家文件。专家文件是按需加载的专业工作手册，不是简单角色描述。

选中专家后必须完整读取其文件。一次指定一个主专家；只有当另一个领域会实质改变判断时，才增加支持专家。不要为了显得全面而一次加载全部专家。

| 问题 | 专家文件 |
|---|---|
| 用户、平台承诺、服务目录、运营模式 | `expert-platform-product.md` |
| 服务边界、API、状态、一致性、事件 | `expert-backend-distributed-systems.md` |
| 集群、调度、网络、存储、故障域 | `expert-cloud-native-infrastructure.md` |
| 模型、训练、推理、加速器、Runtime | `expert-ai-ml-infrastructure.md` |
| SLO、容量、事件、恢复、运维负担 | `expert-sre-reliability.md` |
| 身份、信任区、数据保护、合规 | `expert-security-architecture.md` |
| 成本归属、利用率、单位经济性 | `expert-finops-platform-operations.md` |
| 数据契约、批流语义、血缘和治理 | `expert-data-platform.md` |
| 企业主数据、共享能力和组织归属 | `expert-enterprise-architecture.md` |
| 候选项目、厂商、许可、成熟度和退出 | `expert-technology-research.md` |

## 调用规则

1. 先写清目标领域、待决问题、负责与不负责的内容。
2. 指定一个主专家和必要的支持专家，并说明路由理由。
3. 给专家提供必要项目事实、已有决策和约束，不提供期望答案。
4. 专家按其工作流收集缺失事实，不能用常识补齐会改变结论的输入。
5. 要求专家区分事实、推断、提案、未知和证据等级。
6. 专家只在自己的边界内判断，不决定总体方向或决策状态。
7. 总体架构师比较专家各自优化的质量属性、责任和阶段，解决冲突。
8. 非平凡架构决策先有研究证据，再由总体架构师评审并交给用户确认。

## 专家组合

常见组合：

| 问题 | 主专家 | 支持专家 |
|---|---|---|
| 超大模型在线服务 | AI/ML 基础设施 | 云原生、SRE、FinOps |
| 共享算力资源池 | 云原生基础设施 | AI/ML、SRE、安全、FinOps |
| MaaS 控制面 | 后端与分布式系统 | 平台产品、安全、数据 |
| 商业化准备 | 平台产品与运营模式 | FinOps、安全、企业架构、SRE |
| 开源组件选择 | 技术研究 | 目标模块所属专家 |
| 企业系统集成 | 企业架构 | 后端、安全、数据 |

支持专家只回答会改变主问题的部分。总体架构师不得把多个专家输出简单拼接成架构。

## 研究与裁决门槛

- 没有工作负载、用户或运营模式证据时，保持条件式结论；
- 涉及公开契约、身份、租户、事实源或商业计量时，提高评审等级；
- 涉及产品或厂商选择时，技术研究专家与目标领域专家必须共同参与；
- 涉及 SLO、安全、成本承诺时，相应专家必须审查；
- 只有用户或项目指定决策人可以将建议改为 `Accepted`。

专家输出统一包含：

```text
问题边界：
已确认事实：
关键未知：
关键分析：
证据与置信度：
对总体架构的影响：
对阶段的影响：
风险与存疑项：
建议：
验证与退出条件：
明确不决定的事项：
```
