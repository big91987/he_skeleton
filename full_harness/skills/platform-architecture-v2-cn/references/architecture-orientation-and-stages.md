# 架构设计全景与分阶段引导

## 面向参与者的全景

架构设计把已经确认的产品需求转换成一组能够指导实现的责任、流程、状态、部署和质量契约。它不等于选组件、画部署图或拆微服务。

```text
需求基线
→ 架构驱动与约束
→ 系统上下文与责任域
→ 流程、状态和跨域契约
→ 部署、信任与故障边界
→ 技术策略与验证
→ G2 收口并进入 LLD
```

首次进入或切换阶段时，先向用户说明：

- 当前处于哪一步；
- 这一步用通俗语言解决什么问题；
- 输入来自哪里；
- 会形成哪张图、哪张表或哪条契约；
- 哪些是用户的业务或风险决策，哪些由架构师调研和建议；
- 尚未进入哪些实现细节。

## HLD 七个子阶段

| 子阶段 | 通俗问题 | 主要输入 | 标准产出 | 进入下一步的条件 |
|---|---|---|---|---|
| 0. 定位与共同语言 | 我们现在在做什么，哪些词是什么意思？ | PRD、原型、已有材料 | 全景图、术语解释、当前阶段和未决地图 | 参与者理解讨论层级和决策责任 |
| 1. 架构驱动与约束 | 哪些目标、规模、风险和变化真正决定架构？ | 成功标准、质量要求、环境事实 | 架构驱动因素、已知约束、假设和验证项 | 会改变方向的驱动因素已显式化 |
| 2. 上下文与责任域 | 系统里有哪些责任，哪份信息由谁说了算？ | 价值流、对象、外部依赖 | 系统上下文、能力—事实—责任覆盖表、领域边界 | 所有来源能力和事实均有主责或明确处置 |
| 3. 流程、状态与契约 | 一件事如何从开始走到结束，失败后怎么办？ | 责任域、核心场景 | 调用/控制/计量/观测流、状态机、跨域契约 | 主流程、事实源、成功和失败语义可解释 |
| 4. 部署、安全与故障 | 各部分运行在哪里，谁能访问，哪里坏了影响什么？ | 逻辑模块、质量属性 | 部署视图、网络与信任边界、故障和恢复矩阵 | 主要故障域、降级和恢复责任明确 |
| 5. 技术策略与验证 | 哪些采用、复用或自研，证据够不够？ | 稳定契约、约束、候选能力 | 组件映射、覆盖缺口、原型/基准/故障验证、退出路径 | 技术选择不反向污染产品和领域契约 |
| 6. G2 收口与 LLD 交接 | 方向是否足够稳定，可以开始详细设计了吗？ | 全部 HLD 视图和决策台账 | G2 结论、风险、LLD 输入与责任分工 | 未决项不再改变总体领域、流程、部署或公开承诺 |

这些子阶段允许迭代回退，但不能跳过上游问题后把下游实现当成既定事实。

## 专业概念解释模板

对每个新概念按以下顺序解释：

1. **通俗定义**：一句不依赖专业背景的话；
2. **具体例子**：用当前产品旅程说明；
3. **影响产物**：它影响责任表、流程、状态、部署、代码边界还是验证；
4. **明确不代表**：例如责任域不等于微服务，事实源不等于只能有一份缓存，契约不等于立即定义 API 字段；
5. **用户决策点**：只要求用户判断业务承诺、风险容忍和取舍，不把实现知识测试交给用户。

## 常见层级关系

```text
责任域：谁对一类结果和事实负责
  └─ 逻辑模块：用哪些内部单元履行责任
      └─ 服务或进程：哪些单元需要独立运行和扩缩
          └─ 部署单元：进程具体运行在哪里
              └─ 实现组件：采用什么框架、产品或基础设施机制
```

上层边界会约束下层结构，但不机械决定下层数量。一个责任域可以由多个服务实现，多个责任域也可以在一个模块化单体中保持边界。
