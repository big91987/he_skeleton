# 需求—架构—验证追溯

## 目的

追溯用于发现需求未承接、无来源架构和验证缺口。它不是逐句编号，也不代替需求管理系统。

## 追溯链

```text
需求目标 / 场景 / Story / AC
→ 架构能力或质量属性
→ HLD 领域、模块、流程或契约
→ 架构决策及状态
→ 技术验证证据
→ LLD 责任域
```

## 责任覆盖核对

在提出领域责任、模块清单、总体拓扑或外部依赖边界前，先建立来源清单：

1. 产品目标和成功标准；
2. 用户与运营者的端到端价值流；
3. 功能范围和明确非目标；
4. 核心对象、不变量和生命周期；
5. 数据、策略、资产、运行和计量事实；
6. 性能、可用性、安全、运营与迁移要求；
7. 外部系统、共享平台和基础设施依赖；
8. 当前架构文档已有的责任表、流程节点和图中节点。

形成能力—事实—责任覆盖表：

| source_ref | capability_or_fact | owner_domain | adjacent_domain | lifecycle_or_flow | disposition |
|---|---|---|---|---|---|
| 需求或既有架构位置 | 需要承接的能力或权威事实 | 唯一主责领域 | 使用或派生该事实的领域 | 进入、变更、使用和退出位置 | `Included`, `Merged`, `External`, `OutOfScope`, `Gap` |

清单型架构决策只有在以下条件全部满足后才能发送：

- 每个来源项都有 disposition；
- `Merged` 说明为何生命周期、事实源和故障责任可以合并；
- `External` 仍指出平台接入责任和失败边界；
- 架构责任表、事实源表、流程和图中的同类节点数量及归属一致；
- `Gap` 没有被静默删除，而是进入待补需求、架构决策或技术验证。

## 最小记录

| 字段 | 含义 |
|---|---|
| requirement_ref | 已批准需求、场景或验收条件 |
| architecture_driver | 该需求产生的能力、约束或质量驱动 |
| hld_mapping | 承接它的 HLD 章节、模块、流程或契约 |
| decision_refs | 相关架构决策 ID |
| validation_ref | 原型、实验、基准、故障测试或评审证据 |
| lld_owner | 后续详细设计责任域 |
| status | `Covered`, `Partial`, `Gap`, `OutOfScope`, `Superseded` |

## 何时更新

- 需求基线首次进入架构设计；
- 范围、角色、业务规则、质量承诺或外部依赖变化；
- HLD 新增、拆分或合并领域与模块；
- 技术验证推翻架构假设；
- G2 评审和 LLD 交接。

## 双向检查

从需求向架构检查：每个会影响交付或验收的承诺是否有 HLD 承接和验证方式。

从架构向需求检查：每个公开能力、强隔离、强一致、高可用、商业或合规承诺是否有需求来源或正式决策依据。

以下内容无需逐条追溯：解释性文字、内部重构、可逆实现细节、不会改变外部行为的技术清理。

## 缺口处理

- `Gap`：停止受影响设计，回到需求或架构决策层补齐；
- `Partial`：明确未覆盖部分、影响、负责人和完成条件；
- `OutOfScope`：引用已批准的非目标或阶段边界；
- `Superseded`：保留历史映射并指出替代关系。

不得通过在 HLD 中静默假设需求来关闭追溯缺口。
