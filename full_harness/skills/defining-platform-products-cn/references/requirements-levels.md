# 需求层级与下钻规则

## 目的

在需求定义阶段保持正确粒度：必要内容不遗漏，同时阻止讨论过早进入架构和实现细节。

## 四层模型

| 层级 | 核心问题 | 典型内容 | 退出条件 |
|---|---|---|---|
| L0 方向 | 为什么做、为谁做、承诺什么 | 产品目标、运营模式、成功标准、非目标 | 方向和阶段边界得到确认 |
| L1 业务架构 | 价值怎样产生、责任如何分配 | 角色、价值流、能力、业务对象、生命周期、不变量 | 业务闭环和边界自洽 |
| L2 需求基线 | 系统必须表现出什么行为 | 阶段切片、需求、规则、质量场景、故事、AC | P0 需求可追踪、可验收 |
| L3 架构实现 | 系统如何组织和实现 | HLD、接口、数据、组件、部署、任务 | 不属于本 Skill |

## 必须下钻的情况

只有满足至少一项时，从当前层进入下一层：

- 不下钻就无法判断当前阶段是否完整；
- 两条业务规则发生冲突；
- 无法写出可观察的验收条件；
- 该细节会改变产品边界或运营责任；
- 该细节是用户或外部系统依赖的公开契约；
- 失败处理会改变业务正确性、合规或高成本责任。

## 应停止下钻的情况

出现以下内容时停在当前层并记录为后续输入：

- 数据字段、按钮、页面布局；
- 内部 API 参数、事件格式；
- 数据表和索引；
- K8s 资源、CRD 和调度标签；
- Runtime 参数；
- 组件或供应商配置；
- 微服务拆分；
- 代码任务和测试用例实现。

例外：如果某项内容本身是用户依赖的外部契约，先用业务语义表达约束，技术格式留给架构阶段。

## 粒度校验

对每一项需求依次问：

1. 它对应哪个产品目标？
2. 哪个角色在什么场景需要它？
3. 它处于哪条业务流程？
4. 缺少它会破坏什么业务结果或规则？
5. 如何观察它是否满足？
6. 当前阶段是否必须交付？

无法回答前四项的内容通常不应进入当前需求基线。只能回答第五、六项但不能说明价值的内容，通常是实现任务。

## 确认策略

### 必须确认

- 产品目标和成功口径；
- 运营模式和责任边界；
- 当前阶段范围及非目标；
- 核心业务不变量；
- 具有高成本后果的验收承诺。

### 可以合理假设

- 不改变业务结果的描述和展示细节；
- 可以在架构或设计阶段安全调整的内部机制；
- 已有材料能清楚回答且不存在冲突的事项。

合理假设必须集中记录，不得伪装成已确认事实。
