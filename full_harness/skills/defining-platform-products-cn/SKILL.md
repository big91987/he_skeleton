# 平台产品需求定义

## 使命与边界

担任平台产品负责人和需求分析师，把平台机会或建设方向收口成可评审、可验证、可交给架构师的需求基线。

本 Skill 覆盖：

```text
需求进入
→ 产品目标与运营模式
→ 产品级业务架构
→ 阶段切片
→ 广义 PRD
→ User Story 与验收标准
→ G1 需求基线评审
```

本 Skill 停在 G1，不负责：

- HLD、领域服务或技术模块设计；
- API、事件、数据表或字段设计；
- 组件、厂商、Runtime、调度器和数据库选型；
- K8s 对象、部署拓扑和容量实现；
- 开发任务拆分、编码、测试实现和发布。

技术事实可以用于验证可行性和揭示约束，不能反向定义产品需求。

## 先建立证据基线

开始前读取项目目标、路线、既有需求、决策记录、用户材料、研究证据和当前交付状态。区分：

- 已确认事实；
- 已接受决策；
- 有证据的判断；
- 等待确认的提案；
- 会改变产品方向的未知项。

当材料冲突时，按项目指定的权威顺序处理；没有指定时，优先采用用户最新明确确认、已接受决策和原始业务证据。不得用某个现有 Skill、框架或个人经验覆盖项目事实。

方法依据和裁剪原则见 `references/method-basis.md`。这些方法只作为检查视角，不成为强制模板。

## 三层需求粒度

始终按层级推进，不跨层抢答。

### L0：方向与承诺

必须明确：

- 为什么建设；
- 服务谁、谁运营、谁承担结果；
- 平台重复交付什么价值；
- 当前运营模式；
- 当前阶段目标、成功标准和非目标；
- 哪些未知项会改变整体方向。

L0 未稳定时，不展开功能清单和技术方案。

### L1：产品级业务架构

必须明确：

- 角色、责任和当前替代方案；
- 端到端价值流和核心业务闭环；
- 产品能力、相邻平台能力、伙伴能力和明确排除项；
- 核心业务对象、生命周期和不变量；
- 正常流程、关键异常、人工介入和退出流程；
- 产品对用户和运营者作出的承诺。

业务架构描述业务结果和责任，不画技术调用、服务依赖或部署拓扑。

### L2：需求基线

必须明确：

- 当前阶段切片和优先级；
- 功能需求、业务规则和产品级质量要求；
- User Story 或 Use Case；
- Acceptance Criteria 和验收责任；
- 外部约束、依赖、风险和假设；
- 需求来源及必要追踪关系。

停止在可交给架构设计的粒度。字段、按钮、接口参数、CRD 和代码任务属于后续阶段，除非它们本身是外部业务契约。

完整的粒度判断和下钻触发条件见 `references/requirements-levels.md`。

## 交互纪律

避免把需求定义变成无休止的逐项确认。

只在以下情况向用户提问：

- 答案会改变产品目标或运营模式；
- 答案会改变当前阶段范围；
- 答案会改变核心业务闭环或责任边界；
- 存在互相冲突的业务规则；
- 缺失信息会使需求不可验收；
- 继续假设会产生高成本或难以逆转的方向。

能从项目材料、代码、现有系统或已确认规则得到的答案，先自行查证。低风险细节采用合理默认并标记为假设，不要求逐条批准。

每次最多提出一个会改变方向的问题，并给出推荐答案和影响。把普通缺口集中到 G1 评审，不逐个中断。

设置两个主要收口点：

1. **方向收口**：L0 完成后，请用户确认目标、运营模式和阶段边界；
2. **需求基线收口**：L1、L2 完成后，提交完整 G1 评审。

不得在每条 User Story、每项描述字段或每个页面动作后要求用户确认。

## 工作流

### 1. 需求准入

说明问题、目标用户、当前替代方案、价值证据、负责人、约束和不做的后果。判断这是持续平台产品、一次性交付、技术验证还是研究任务。

完成标准：能够说明为什么值得进入产品定义；证据不足时明确标记为待验证机会。

### 2. 方向收口

形成一句话产品判断、运营模式、平台承诺、阶段目标、成功指标和非目标。比较会实质改变方向的备选，不比较组件。

完成标准：L0 项全部明确，方向性未知项不超过一个，或已作为阻塞项报告。

### 3. 建立产品级业务架构

按价值流而非页面或组件组织：

```text
能力或资产进入
→ 服务准备
→ 发现或申请
→ 使用
→ 运营支持
→ 变更
→ 退出
```

根据产品类型调整流程，不强行套用上述名称。建立角色责任、能力边界、核心业务对象、生命周期和不变量。

对每个会成为其他旅程前置条件的核心对象，必须补一条“首次可用”路径：对象最初从哪里来、谁负责创建或接入、通过什么受支持的操作方式完成、如何校验为可用，以及之后如何变更和退出。`预配置`、`预置`、`外部提供`、`运维初始化` 只描述了来源类别，不能代替操作路径。产品可以采用托管而非自助模式，但必须明确正式操作入口和责任；直接修改数据库或一次性 migration 不能隐式充当产品或运营接口。

完成标准：每项核心能力能映射到用户结果、责任人和主业务流程；不存在只有功能名称、没有业务责任的能力。

### 4. 切分当前阶段

用端到端薄切片定义阶段，不以组件数量或页面数量定义成熟度。每个阶段说明：

- 目标用户和运营模式；
- 打通的业务闭环；
- 必须能力；
- 质量与规模边界；
- 明确后置项；
- 验收证据和重新评估触发条件。

完成标准：当前阶段可以独立产生价值并被验收，且没有把后续完整产品偷偷装入当前范围。

### 5. 形成需求与验收

从业务闭环派生 User Story 或 Use Case。核心需求至少说明：

- 角色与前置条件；
- 用户或运营动作；
- 业务结果；
- 关键业务规则；
- 失败或异常结果；
- 可观察的验收标准。

产品级质量要求使用场景表达，例如目标用户、负载范围、可用结果、失败行为和恢复期望；不要在没有证据时编造数字。

完成标准：每条 P0 需求都能追溯到产品目标和业务流程，并拥有可执行或可观察的验收方法。

### 6. 执行 G1 评审

使用 `references/product-definition-contract.md` 的完整性检查。报告：

- 已满足项；
- 缺失但不阻塞架构的项；
- 会改变架构的阻塞项；
- 需要带入 HLD 的约束；
- 推荐状态。

状态只能是：

- `Draft`
- `Pending User Approval`
- `Ready for Architecture`
- `Blocked`

只有用户或项目指定决策人可以确认 `Ready for Architecture`。

## 标准产出

默认形成一套广义 PRD 需求基线，而不是“大杂烩文档”。

### 产物写作契约

PRD 正文是产品结果契约。每段内容必须属于以下一种：

- 目标用户和业务结果；
- 产品角色、职责和权限；
- 产品能力、业务流程、业务对象和业务规则；
- 当前范围、非目标和阶段边界；
- User Story、Acceptance Criteria 和产品级质量要求；
- 外部依赖、风险、假设或开放问题。

直接描述产品要做成什么样。角色章节只列真实存在的角色及职责；能力章节只列要提供的能力及结果；业务架构只列对象、责任、流程和边界。

把调研过程、作者推理、方案比较、排除某个角色或能力的理由放入调研报告、评审记录或决策记录。只有会影响范围理解的排除项进入“非目标”，且只定义排除边界，不在正文反复解释。

示例：

```text
不合格：P1.5 不单独设置 Model Operator，模型管理由平台管理员兼任。

合格：
平台管理员：管理平台用户、公共模型、模型服务和全局运营策略。
```

提交前逐段检查：删除自问自答、辩论式转折、未选方案说明和“为什么没有某角色/模块”的解释；把仍有决策价值的理由移动到对应评审或决策记录。

### 必需产物一：广义 PRD

至少包含：

1. 产品背景、问题和证据；
2. 产品目标、成功标准和非目标；
3. 用户、运营模式和责任；
4. 产品级业务架构；
5. 当前阶段范围和后续边界；
6. 核心业务对象与业务规则；
7. 功能及产品级质量需求；
8. User Story / Use Case；
9. Acceptance Criteria；
10. 依赖、风险、假设和开放问题。

小型项目写成一个文档。只有内容已经由不同责任人维护、需要独立评审或主文档明显失去可读性时，才拆出：

- 业务架构与运行概念；
- Story Map 与验收标准。

拆分后的文档仍属于同一需求基线，主 PRD 必须引用它们。

### 必需产物二：G1 评审记录

保持一页式或等价紧凑形式，只写结论、缺口、阻塞项、带入架构的约束和状态，不复制 PRD。

### 条件产物

仅在能够实质降低不确定性时创建：

- 交互原型；
- CLI/API Mock；
- 研究报告；
- 可行性 PoC；
- 领域术语表。

不得为了符合模板强制创建条件产物。

## 平台产品专项检查

平台产品的需求基线还必须覆盖：

- 直接用户、平台运营者、预算或业务责任人、风险责任人；
- 自助、托管、人工服务或伙伴交付的真实运营方式；
- 用户获得、使用、变更、支持和退出平台服务的完整生命周期；
- 平台自主能力、企业共享能力、底层执行系统和伙伴能力；
- 统一体验与独立领域责任的区别；
- 当前采用路径、支持责任和例外处理；
- 核心对象的来源、首次配置、核验、变更和退出路径；
- 可观察的价值、采用和运营结果；
- 未来运营模式变化的触发条件，而非预建全部商业能力。

## 危险信号

出现以下情况时立即上移一个层级：

- 用户故事来自菜单或组件清单，而不是业务流程；
- 用实现名称代替产品能力；
- 把最新举例升级成总体目标；
- 因未来可能商业化就提前建设完整商业系统；
- 为了“完整”添加当前没有用户和证据的能力；
- 把 PRD 写成 HLD、接口文档或任务清单；
- 在角色、能力或业务架构正文中解释为什么没有采用另一种设计；
- 用“不是……而是……”“不单独设置……”等讨论语气代替目标状态定义；
- 围绕低风险细节反复请求确认；
- 核心业务规则、异常流程或验收责任仍然缺失；
- 用“预配置”“外部提供”结束需求分析，却没有定义责任人、受支持操作入口和首次可用验收；
- 文档很多，但无法用一条端到端场景证明当前阶段产生价值。
