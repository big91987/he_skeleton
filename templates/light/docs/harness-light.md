# Light development workflow

Open an Issue to start one workflow run. Contributors with write, maintain or admin permission can start the Agent; for an outsider-created Issue a contributor starts it manually from Actions. Subsequent natural-language Issue comments are read by the active stage Job, not new workflow triggers. Each user turn starts one `codex exec` or `codex exec resume`; the same Issue keeps the same native Session across turns and Jobs. An ordinary reply continues the current Job. Confirming a document runs its current stage and automatically starts the next Job, without a separate intent-classifier call.

The Agent reads project entries and selects native Skills progressively. Only the current stage catalog is enabled for each execution. Requirements and design produce reviewable files and ask for confirmation. A clear confirmation returns the adjacent next stage; the next Job resumes the Session and does that stage’s work. The same confirmation cannot approve both requirements and design. Questions remain conversation, without a separate classifier or model reviewer. Existing materials can be reused as the stage baseline.

The Agent output has exactly three fields: `next_state`, `message`, and `artifacts`. The input `stage` is the current checkpoint; `next_state` is where the following conversation resumes. Values are `requirements`, `design`, `development`, and `done`. Clarifications, questions, waiting for confirmation and blockers keep the same stage and are explained in the message; they are not separate workflow states. A design confirmation hands off to the development Job, which runs implementation and checks before returning `done`.

The controller retains document versions and the original user message as evidence when the Agent advances a stage. It does not run a second intent classifier or ask the Agent to copy approval quotes. A malformed result cannot change the checkpoint. `done` requires a matching real check result; a failed publication retries transport without repeating the Agent call. Existing light Sessions migrate their document records and keep their native Session IDs.

Actions shows `authorize → restore → requirements → design → development`. `restore` reads the persisted checkpoint without calling a model. Each business stage has its own Job, log, summary and downloadable artifacts; the Job may contain multiple Codex calls separated by user replies. Jobs not reached in this run are skipped; a skipped earlier stage does not undo its saved approval. Returning to an earlier stage records the checkpoint and ends this run; manually start the same Issue from Actions to reopen the earlier stage. A finished native Job cannot be rewound by this template. The Agent is instructed to acknowledge the request before work and share meaningful progress as needed. The framework accumulates its progress messages in one collapsed Issue comment per execution, updating that comment while retaining earlier messages. The fold summary shows the cumulative message count. Both text and complete native Agent/lifecycle events accumulate in arrival order for the whole execution, including repeated native item IDs across turns. The final result is posted as a separate new comment. The framework writes no progress narrative and invokes no extra model; tool events remain in Actions logs. For CLI events without a phase field, further work or another Agent message releases the preceding message; the last message is left to the final-result publisher so it is not posted twice. Transport failures leave progress in the logs and do not stop the Agent. Issue replies contain the Agent's actual words and expandable documents at useful points; downloads are on the linked run.

The native Stop Hook is registered only in the development Job and runs checks when the Agent claims development delivery (`next_state: done`). It checks configured project commands and Python format/lint, and asks the same running Codex to repair failures. Requirements, design and ordinary questions do not run those development checks. There is no additional independent model review in this profile. Passing configured checks proves only their scope.

Owner configuration is `.harness/full.json`: entries, stage Skills/instructions/document paths, checks, time limits. Configure real product checks before development; an empty checks list cannot pass delivery. The full template's entry and review configuration is retained for compatibility but not executed by the light profile.

Private state and Codex sessions live under `FULL_STATE_ROOT/light/<repository-and-branch>/<issue>/`. They are separate from full-template tasks and never uploaded as artifacts. Each turn retains its prompt, raw JSONL, structured result and check logs. Runtime failures retain the workspace/session; manually start the same Issue from Actions to resume. Comments alone do not restart an ended run. A rerun of an already started event does not start a second Codex execution. Deduplication records the user event and stage together, so stage handoff is allowed and replay of a completed Job cannot rerun the Agent. A completed event can retry publication without another model call. A failed or cancelled preceding Job cannot start a downstream stage. Base-revision changes require reconciliation; this initial profile uses one persistent Runner.

Install from a committed toolbox revision with `python3 scripts/install_light.py <product-checkout> --ref <commit>`. `--ref` defaults to HEAD. Installation preserves owner-edited templates and the existing full workflow. Enable only the chosen workflow for automatic Issue events; disable the other through Actions or explicitly separate their triggers. Commit and push the installed files before trying the workflow.

Try: open an Issue, inspect the document, ask a question, request an edit, then confirm it. Verify that each user turn has one native Session start/resume within the same workflow run, that each stage exposes its own Skill catalog, and that the Session ID stays the same when Jobs change. Continue through design and development, inspect actual checks and the draft PR. Merge remains a human operation.

Upgrading the earlier two-Job light template requires updating the owner-managed workflow together with the runtime. The installer preserves existing workflow files; copy the reviewed `templates/light/.github/workflows/harness-light.yml` into the product workflow explicitly, and update the owner’s AGENTS.md and workflow guide to describe the separate stages. Existing light Session IDs, stages, documents and approvals remain valid after reconciling the execution revision.

The folded progress comment shows execution status separately from the business stage. Native message/status events retain the complete outer JSON, including `type`, `item` and the original `text` string. The final download includes `agent-events.json` (Agent messages and lifecycle events, excluding tool output) and `agent-result.json`. Private runtime paths are redacted. `item.completed` is not a whole execution completing; `turn.completed` finishes a native turn, and process success/failure determines the final execution label. Ending an execution does not mean the project task is done. A forced Runner termination may prevent the last comment update; the linked Actions run remains authoritative.

Replies during execution do not interrupt or steer the current CLI. The same Job polls the Issue every 15 seconds after the CLI returns. New comments are processed in API creation order, with a persisted comment-ID cursor. Bots, empty comments, framework markers, already handled messages and users without write/maintain/admin permission are ignored. Permission/API failures do not consume the unread message. The handoff message and its original timestamp persist across Jobs so one approval cannot approve two stages. No extra classifier or fixed reply command is introduced.

The waiting Job holds its persistent Runner slot. The template budgets five hours per stage including execution/waiting, and a six-hour Job timeout leaves room for an in-flight Agent call and artifact upload. Keep the configured agent_timeout and publication time within the one-hour cushion when customizing this template. Polling currently rereads comment pages, so very long Issues increase API usage. The Python deadline is checked between calls; it cannot interrupt an Agent call at exactly five hours. Closing the Issue stops waiting on the next poll, but does not interrupt an active CLI. Cancellation or hard timeout can interrupt the process: checkpoints survive, but the same Job process cannot be recovered. Restart manually from Actions with the same Issue and reviewed code revision. Normal replies stay in the same run; timeout/restart and backward-stage changes are explicit exceptions. Concurrent runs for one Issue are serialized; a single Runner still serves one Job at a time.

Reviewable small text documents are embedded in the final Issue reply immediately. GitHub artifact upload happens after the stage Job ends, so downloads are not available while that Job is waiting. Per-turn public artifacts are retained under `turns/<turn>/`; they do not overwrite earlier outputs. Larger documents and binary previews still require stage completion for the download package in this minimal version. Raw private Session logs never enter the package.

`python3 full_harness/light.py <stage> --wait-seconds 18000` enables this behavior. Omitting that option retains the older one-turn runtime for owner-managed workflows that have not been upgraded. Updating the template requires removing its `issue_comment` trigger as well as enabling waiting on restore and all three stages; otherwise replies would also enqueue redundant runs.

Stage deliverables are defined in AGENTS.md and the stage Skills. The design handoff path is an index, not the only output: include the prototype, HLD, contracts, required decision records and evidence in the reviewed artifact set. The light prompt does not pass the legacy requirements/design `artifact` hint to the Agent. Development keeps its verification-record path because the delivery check consumes it.

On first installation into an existing repository, append the template's stage-deliverables section to AGENTS.md while retaining owner rules. Upgrades preserve owner files: explicitly reconcile AGENTS.md, docs/README.md and .harness/full.json against the selected templates. Existing sessions also need their saved configuration reconciled before resuming; re-read the updated project instructions and recheck earlier deliverables. Installing runtime files alone does not complete this migration.

Progress never replaces earlier raw events with the latest event and never truncates earlier text. If GitHub comment capacity is exceeded, numbered continuation comments retain the complete text and JSON segments; normal runs use one folded progress comment. Old progress records can recover their full event history from the retained current-execution JSONL without invoking the model or changing task state.
